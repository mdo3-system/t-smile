# スキル：TIF原図 → 間取り工房JSON 生成手順

パイロット3件（PLAN-2387-P01/P02/P03、2026-11-17 Muse実施）で確立した方式。標準的な2階建てで床面積±1.5%・主要居室±1帖以内を再現できた実績に基づく。

## §1 前提と単位
- 間取り工房の座標は **1単位＝910mm**。座標は0.5単位（455mm）刻みが基本
- 換算：1単位²＝0.8281㎡／1帖＝2単位²（アプリの帖換算は1.6562㎡/帖）／1坪＝3.3058㎡
- 原図は910モジュール前提。寸法チェーンの合計が単位の整数倍になるか必ず検算する

## §2 フレームとプランの対応付け
- TIFはマルチフレーム（1ファイルに複数シート）。**フレーム番号とプラン番号は一致しない**
- A2期（おおむね15年以上前）：1フレームに平面図（複数階）と立面図がまとまっていることが多い。1フレーム＝1プランのことが多いが、大きなプランは階ごとにフレームが分かれる場合もある（実例：SCAN2387のP02はフレーム2＝1階、フレーム3＝2階）
- A3期（以降）：平面図は階ごと（1F/2F/3F）、立面図も別シート。1プラン＝複数フレームの組になるため、仕分けと対応付けが前提
- シートの向き（回転）はフレームごとに異なる。表題欄と文字の向きで正立を判断する（90度回転が逆だと文字が上下逆になる）
- 立面図・断面図は対象外。平面図シートだけを使う
- 対応付けの手がかり：シート内のプラン番号表記、面積表、plans_zbufのWebP（PLAN-{案件}-P{nn}_{階}F_2d.webp）の間取りとの一致

## §3 読み取り手順
1. **面積表を最初に読む**：建築面積・階別床面積・延床面積が正解値。㎡→単位²は ÷0.8281 で換算し、各階の「部屋の合計がこの値になる」ことを設計目標にする（例：58.79㎡＝71単位²）
2. **寸法チェーンを読む**：上面・左面・下面の寸法線から通り芯位置（単位座標）を確定する。チェーン合計と建物外形を検算する
3. **ピクセル較正**（チェーンが読みにくい場合）：原図画像の行・列方向のインク量分布（射影）を取り、外壁線のピクセル位置から原点と単位ピクセル数を決める。スキャンは縦横で数%の伸縮差があるため、縦横別々に較正する
4. **部屋名と帖数を読む**：帖数表記のある部屋は 帖数×2＝単位² を目安に寸法を決める。水回り・廊下・収納は残りの空間から割り当てる
5. **開口部を読む**：サッシ記号（引き違い・出窓等）、FL表記（例 FL+450、FL+1,050）、扉の開き弧、寸法表記（例 W1.64×H1.30 のように図面に直接書かれている場合がある）

## §4 JSON仕様（全体・壁・部屋・階段）
トップレベル：
```json
{
  "planId": "PLAN-2387-P01",
  "projectTitle": "PLAN-2387-P01",
  "modulePitch": 910,
  "gridDivisions": 2,
  "floors": { "0": {空の階}, "1": {1階}, "2": {2階}, "3": {空}, "4": {空} },
  "savedAt": "ISO日時"
}
```
各階オブジェクトは `rooms / walls / pillars / openings / fixtures / stairs / boxes3d / strokes / stamps / memos / polyPillars` の配列を持つ（使わないものは空配列）。

壁：`{"id": 一意, "x1": , "y1": , "x2": , "y2": , "wallType": "wall"}`（単位座標、水平・垂直のみ）
- 外周は閉じた輪郭にし、室内の間仕切り壁も部屋境界に沿って引く
- **玄関土間（`DOMA`）と上り框（`wallType: "agarikamachi"`）**：玄関エリアは「`玄関土間`（`type: "DOMA"`：床レベル-180mm）」と「`玄関ホール`（`type: "GENKAN"` または `"HALL"`）」に分離し、境界線に `wallType: "agarikamachi"` の壁セグメントを配置する（`DOMA` も延床面積に算入されるため合計面積は変わらない）

部屋：`{"id", "kind": "room", "type": 種別, "name": 部屋名, "isAutoDetected": false, "points": [{"x","y"}...], "x","y","w","h", "centroid": {"x","y"}, "areaM2", "tsubo", "jo", "color2d": "rgba(226, 232, 240, 0.65)", "color3d": "#f1f5f9", "customName": 部屋名}`
- areaM2/tsubo/jo はポリゴン面積から計算して入れる（アプリ側でも再計算されるが、書式を実例に合わせる）
- 種別（type）の例：LDK / YOSHITSU（洋室）/ WASHITSU（和室）/ KITCHEN / BATH / WASHROOM（洗面所）/ TOILET / GENKAN（玄関ホール）/ DOMA（玄関土間）/ HALL（廊下・ホール）/ STORAGE（収納・納戸・押入）/ STAIR / BALCONY
- **部屋ポリゴンの和集合がその階の床面積になるよう、隙間なく・重なりなくタイル状に敷き詰める**のが精度の要。壁だけのJSONでも v2.16.0 の自動認識で面積は再現できるが、部屋名が付かないため、納品物は部屋まで作り込むこと

階段：`{"id", "kind": "stair", "type": "STAIR", "category": "STAIR", "shapeType": "STRAIGHT", "points": [4隅], "widthMm": 910, "steps": 14, "treadMm": 220, "riserMm": 200}`

## §5 開口部仕様
正規フォーマット（アプリの生成コードと同一形式）：
```json
{"id", "category": "window"|"door",
 "type": "WINDOW"|"SWING_DOOR"(片開き)|"SLIDING_DOOR"(それ以外),
 "sashType": 種別, "doorFit": 種別（sashTypeと同値）,
 "leafCount": 枚数, "leafWidthMm": 幅/枚数,
 "x": 中心の単位座標, "y": 同, "orient": "h"|"v", "flip": false,
 "widthMm", "heightMm", "sillMm": 窓台高さ（掃き出しは0）,
 "widthP": widthMm/910, "label": "窓 (W1650×H1300)"等, "isWin": true|false}
```
種別（sashType/doorFit）：hikichigai（引き違い）/ katabiki（片引き）/ katahiraki（片開き）/ oyako（親子）/ fix / oredo（折戸）/ closet / demado（出窓）/ tatesuberi / yokosuberi / agesage
寸法の目安：居室腰窓 1650×1300・FL+800／掃き出し 1820〜2560×2000・FL+0／水回り小窓 800×900・FL+1100／玄関ドア 910×2200（katahiraki）／室内ドア 800×2000／トイレ 700×2000。原図にFL表記や寸法表記があればそちらを優先する

## §6 面積の扱い（除外と算入）
- ベランダ・バルコニー・ポーチは原則 **床面積に算入しない**：部屋オブジェクトに `"excludeFloorArea": true` を付ける
- ただし原図の面積表に含まれていると判断できる場合は算入する（実例：P01の2階ベランダ相当部分は面積表59.62㎡に含まれていたため `"excludeFloorArea": false` を明示して算入した）。面積表との差で判断する
- 出窓は床面積に算入しない（窓として開口部で表現する）
- 車庫は面積表に含まれていれば算入する。車庫に面積表記（例 24.84㎡）があればそれに合わせる

## §7 照合手順（間取り工房 v2.16.0 のQA照合パネル）
1. 生成JSONを「📂 読込・復元」から読み込む（「部屋が空の階は自動認識」チェックは、部屋を作り込んだJSONでは結果に影響しない）
2. 上部バー「📋 QA照合」を開き、目標値（1F/2F/3F/延床の㎡、部屋別帖数「LDK:17.5, 和室:8」形式）を登録する（localStorageに保持される）
3. 表示される差分と合否を確認する。アプリ内蔵の合否基準：階別面積 **±0.30㎡以内でOK**、部屋帖数 **±0.25帖以内でOK**
4. 本作業の合格基準：階別 **±2%以内**、帖数表記のある居室 **±1帖以内**、開口部の欠落なし
5. **注意：QAの部屋照合は同名の部屋を合算しない**（最初に一致した1室だけを照合する）。LDKを2ポリゴンに分けて作ると片方だけで判定されるため、照合対象の部屋はなるべく1ポリゴンで作る

## §8 既知の落とし穴（パイロットの知見）
- **開放的なLDKは過小になりやすい**：キッチン・ホールとの境界が曖昧で、実測より数帖小さくなった（P02：1階LDK 12.2帖／図面14.5帖）。面積表の残差配分でLDK側を広めに取る
- **複合ブロック型は初回で −3〜4% 残りやすい**（車庫＋複数ブロックがずれて接合するプラン）。ブロックごとの寸法チェーンを個別に確定してから接合する
- **原図とサイト詳細ページの食い違い**：実例では2階和室が原図3帖・詳細ページ6帖と異なった。常に原図を正とする
- スキャンの回転・伸縮：フレームごとに向きが違い、縦横の伸縮差も最大3%程度ある。ピクセル実測だけで決めず、寸法チェーンと必ず突き合わせる
- 部屋ポリゴンの重なりは床面積から自動控除される（v2.15.1以降）が、帖数の表示は各部屋の値のままなので、重なり前提の作り方はしない

## §9 出力と台帳
- ファイル名：`PLAN-{案件}-P{nn}.json`、保存先は指示書 §3 のフォルダ
- 台帳（progress.md）に1プランごとに記録：プラン番号／使用フレーム番号／階別 目標㎡・実測㎡・差%／主要居室の帖数照合／開口部数／未確認事項
- 読み取れなかった箇所は推測で埋めず「未確認」と記録する
